2. ภาพรวมระบบและขอบเขตงาน
------------------------------------------------------------
เส้นทางการทำงานหลัก:
  Browser/Frontend -> PC2 Nginx -> PC3 Flask Backend -> PC1 FastAPI AiEngine -> Forge

PC1:
  FastAPI AiEngine รับงานและควบคุม WebUI Forge ที่เปิดผ่าน Stability Matrix
  FastAPI ใช้พอร์ต 8000 ส่วน Forge ใช้พอร์ต 7860 ภายในเครื่อง PC1

PC2:
  Nginx และจุดที่ผู้ใช้เข้าใช้งาน Frontend
  โค้ด Nginx/Frontend ไม่อยู่ในชุดไฟล์ Backend ปัจจุบันที่ใช้ส่งต่องานนี้

PC3:
  Flask, JWT, SQLite, คิวงาน, ภาพอัปโหลดชั่วคราว และภาพผลลัพธ์
  Backend ใช้พอร์ต 5000 และส่งโทเคนบริการไป AiEngine

สิ่งที่ทำในแชตนี้เป็นการตรวจโปรเจกต์ เตรียม Backend ก่อนเดโม
และปรับ Backend ให้ใช้สัญญา API ของ AiEngine ได้
ยังไม่มีหลักฐานว่ารวม branch เข้ากับ main หรือทดสอบระบบครบสามเครื่องแล้ว

3.4 ตรวจค่าก่อนเปิด Backend ใน VLAN/production
  - ตรวจ SECRET_KEY, JWT_SECRET_KEY และ AI_SERVICE_TOKEN
  - ความลับต้องไม่เป็น placeholder และยาวอย่างน้อย 32 ตัวอักษร
  - SECRET_KEY และ JWT_SECRET_KEY ต้องเป็นคนละค่า
  - ตรวจ AI_SERVICE_URL ว่าเป็น HTTP/HTTPS URL
  - โหมด VLAN ไม่ยอมให้ชี้ AI ไป localhost
  - CORS ต้องระบุ origin จริง และปิด debug นอก development
  - ถ้าค่าผิด ระบบปฏิเสธการเริ่มบริการพร้อมข้อความอธิบาย

3.5 เพิ่มสิทธิ์ดาวน์โหลดภาพ
  - เจ้าของภาพใช้ Authorization: Bearer <JWT> ดาวน์โหลดได้
  - หรือใช้ result_url ที่ Backend ลงลายเซ็นและกำหนดอายุให้
  - บัญชีอื่นอ่านงานหรือภาพของเจ้าของเดิมไม่ได้
  - ไม่มี JWT/ลิงก์ที่ใช้ได้จะถูกปฏิเสธ
  - ลิงก์หมดอายุให้เรียก API อ่านงานใหม่เพื่อรับ result_url ใหม่

3.6 กู้สถานะงานหลัง Backend เริ่มใหม่
  - งาน queued ที่บันทึกไว้ถูกนำกลับเข้าคิว
  - งาน processing ที่ถูกขัดจังหวะถูกเปลี่ยนเป็น failed และให้ผู้ใช้ส่งใหม่
  - ไม่ได้ประมวลผลภาพต่อจากจุดที่ Forge ทำค้างไว้
  - เปิด/ปิดด้วย RECOVER_JOBS_ON_STARTUP
  - คำสั่งบำรุงรักษาปิด recovery เพื่อไม่เริ่มงานระหว่าง backup/cleanup

3.7 ตรวจและจัดเก็บผลลัพธ์ AI
  - ต้องเป็น HTTP 200 และ Content-Type image/png พร้อมข้อมูลภาพ
  - ใช้ Pillow ตรวจว่าเป็น PNG ที่อ่านได้และไม่เกิน MAX_OUTPUT_PIXELS
  - ตรวจ seed ใน X-LUMA-Seed ให้อยู่ในช่วง uint32
  - เขียนไฟล์ชั่วคราวก่อนแทนที่ปลายทาง เพื่อลดการอ่านไฟล์ที่เขียนไม่ครบ
  - เก็บชื่อภาพเป็น <job-id>.png และบันทึก provider/seed/เวลาสำเร็จ
  - คำตอบผิดหรือบริการล้มเหลวทำให้งาน failed พร้อมข้อความสำหรับผู้ใช้
  - ล้างไฟล์ต้นทางของงานแก้ไขภาพเมื่อ worker จบงาน

3.8 เพิ่มกรณีทดสอบข้อมูลผิดและบริการล้มเหลว

ความสามารถฝั่ง AI ที่ตรวจพบ:

4.1 สิ่งที่เพิ่มใน Backend เพื่อใช้กับ AiEngine
  - รับ/ตรวจ/ส่ง model, loras, sampler, scheduler, cfg_scale, clip_skip, style_preset
  - Generate ส่ง JSON ส่วน Edit ส่ง multipart form
  - loras ของ Edit ต้องเป็นข้อความ JSON array ก่อนส่งไป AiEngine
  - เก็บตัวเลือกในตารางใหม่ job_ai_options ซึ่งสัมพันธ์กับ Job แบบหนึ่งต่อหนึ่ง
  - job.ai_options คือค่าที่ผู้ใช้ขอ และ job.ai_result คือค่าที่อ่านจาก header AI
  - งานเก่าที่ไม่มีแถวตัวเลือกจะคืนทั้งสองช่องเป็น {}
  - อ่านค่าที่ AI ใช้จริง ได้แก่ model/sampler/scheduler/style/steps/clip_skip/CFG
  - ถ้า AI รายงาน steps ที่ใช้จริง ระบบปรับ job.steps ตาม header นั้น
  - seed และ provider ยังคงคืนในช่องเดิมของ Job
  - ไม่ได้เก็บทุก header เช่น queue wait/execution time และ LoRA header ใน ai_result
  - ปิดการตาม HTTP redirect ของคำขอ AI ที่เพิ่ม/ปรับ เพื่อไม่ส่ง service token ต่อไป

4.2 API ตัวเลือกและพรีวิวใหม่
  - เพิ่ม ai_catalog.py ให้ Frontend อ่านตัวเลือกผ่าน Backend ด้วย JWT
  - ส่ง service token จาก Backend ไป AiEngine อัตโนมัติ
  - เปลี่ยน preview_url ในรายการโมเดล/LoRA เป็นลิงก์ของ Backend
  - พรีวิวใช้ JWT หรือลิงก์ลงลายเซ็นที่ผูกกับชนิดและชื่อภาพ
  - รับเฉพาะ PNG/JPEG ที่ตรวจได้ ไม่เกิน 2 MiB และจำนวนพิกเซลที่กำหนด
  - เวลาเชื่อมต่อผิดพลาดคืน JSON error โดยไม่ส่งรายละเอียดภายใน AI ให้ผู้ใช้

4.3 ปรับ timeout
  - AI_CONNECT_TIMEOUT=5 วินาที
  - AI_READ_TIMEOUT=600 วินาที สำหรับงานสร้าง/แก้ไขภาพ
  - AI_METADATA_TIMEOUT=10 วินาที สำหรับตัวเลือก/พรีวิว/สถานะคิว
  - AiEngine รุ่นอ้างอิงมี queue timeout 180 และ Forge read timeout 300 วินาที
  - หาก .env เดิมมี AI_READ_TIMEOUT=180 ต้องแก้เอง เพราะไม่ได้คัดลอกทับ .env จริง


5. API ที่คนทำ Frontend/ผู้รับงานต่อต้องใช้
------------------------------------------------------------
เปิดได้โดยไม่ใช้ JWT:
  POST /api/v1/auth/register       {username, password}
  POST /api/v1/auth/login          {username, password}
  GET  /api/v1/health              สถานะ Backend และ dependencies

ต้องใช้ Authorization: Bearer <access_token>:
  GET  /api/v1/auth/me
  POST /api/v1/jobs/generate       JSON; คืน 202 และ {job: ...}
  POST /api/v1/jobs/edit           multipart/form-data; คืน 202 และ {job: ...}
  GET  /api/v1/jobs                รายการงานของเจ้าของ; limit 1-100, default 20
  GET  /api/v1/jobs/<job_id>       อ่านสถานะ/ผลลัพธ์ของเจ้าของงาน
  GET  /api/v1/ai/models
  GET  /api/v1/ai/loras
  GET  /api/v1/ai/samplers
  GET  /api/v1/ai/schedulers
  GET  /api/v1/ai/settings
  GET  /api/v1/ai/styles
  GET  /api/v1/ai/styles/<style_id>
  GET  /api/v1/ai/queue/status     สถานะคิวรวมของ AiEngine

ใช้ JWT หรือ signed URL:
  GET /media/<filename>
  GET /api/v1/ai/preview/model/<name>
  GET /api/v1/ai/preview/lora/<name>

Generate รับค่าพื้นฐาน:
  prompt: ข้อความ 3-1000 ตัวอักษร
  negative_prompt: ข้อความไม่เกิน 1000 ตัวอักษร
  width/height: 256-1024 และหาร 64 ลงตัว; default 512
  steps: 1-50; default 20
  seed: 0-4294967295; Backend สุ่มให้เมื่อไม่ระบุ

Edit รับ image (PNG/JPEG/WebP), prompt, strength 0-1 และ seed
  strength default 0.65; จำกัดภาพต้นทาง 4194304 พิกเซล
  AiEngine Edit รุ่นอ้างอิงไม่ได้รับ steps/negative_prompt แบบเดียวกับ Generate
  อย่าสัญญากับ Frontend ว่าสองช่องนี้ปรับงาน Edit ได้ผ่าน Backend ปัจจุบัน

ตัวเลือกเพิ่มเติมที่ใช้ได้กับ Generate/Edit:
  model/sampler/scheduler/style_preset: ข้อความไม่เกิน 255 ตัวอักษร
  cfg_scale: 1-30; clip_skip: 1-12
  loras: list ไม่เกิน 8 รายการ; แต่ละรายการเป็นชื่อ หรือ {name, weight}
  LoRA weight ที่ Backend ยอมรับ: 0-2
  ดึงชื่อโมเดล/LoRA/style ที่มีจริงจาก API ตัวเลือก แทนการใช้ชื่อในตัวอย่างตรง ๆ

ตัวอย่าง Generate:
  {
    "prompt": "a paper city in daylight",
    "width": 512,
    "height": 512,
    "steps": 20,
    "seed": 42,
    "model": "ชื่อโมเดลที่มีจริง",
    "loras": [{"name": "ชื่อ LoRA ที่มีจริง", "weight": 0.7}],
    "sampler": "Euler a",
    "scheduler": "Karras",
    "cfg_scale": 7.5,
    "clip_skip": 2,
    "style_preset": "anime_illustrious"
  }

ตัวอย่าง field ของ Edit:
  image=<ไฟล์ภาพ>, prompt=make the sky warm, strength=0.6
  loras=[{"name":"ชื่อ LoRA ที่มีจริง","weight":0.7}]
  model/sampler/scheduler/cfg_scale/clip_skip/style_preset ส่งเป็นข้อความในฟอร์ม

สถานะงาน: queued -> processing -> completed หรือ failed
  progress เป็นช่วงสถานะ: เริ่ม 0, processing 15, completed 100, failed 0
  ค่า 15 ไม่ใช่เปอร์เซ็นต์จริงจาก Forge
  ใช้ result_url ที่ Backend คืนให้เมื่อ completed
  อ่าน error ของงานเมื่อ failed; HTTP 202 หมายถึงรับงาน ไม่ได้หมายถึงสร้างภาพสำเร็จ
  ข้อผิดพลาด API ใช้ {"error":{"code":"...","message":"..."}}

9. งานที่คนรับช่วงต้องทำต่อ ตามลำดับที่แนะนำ
------------------------------------------------------------
ลำดับ 1: ตรวจรุ่นโค้ดและ environment ของแต่ละเครื่อง
  - ตรวจว่า Backend และ AiEngine ใช้รุ่นที่ตกลงร่วมกัน
  - ตรวจ IP/port/service token และแก้ AI_READ_TIMEOUT ใน .env เดิมถ้ายังเป็น 180
  - เปิด Forge และ FastAPI บน PC1 แล้วให้ Backend health เห็น ai_service=ok

ลำดับ 2: ทดสอบกับ AiEngine จริง
  - เริ่มด้วย development-procedural ถ้าต้องแยกปัญหาเครือข่ายออกจาก GPU
  - ทดสอบ Generate/Edit พร้อม model, LoRA, style และ sampler/scheduler
  - ตรวจผล PNG, seed และค่าที่คืนใน ai_options/ai_result
  - ทดสอบ catalog และ preview_url ที่เบราว์เซอร์เรียกผ่าน Backend
  - ทดสอบกรณี token ไม่ตรง AI หยุดทำงาน และ timeout

ลำดับ 3: ต่อ Frontend และ Nginx
  - ส่ง JWT ใน API ส่วนที่ต้องยืนยันตัวตน
  - อ่านรายการตัวเลือกจาก /api/v1/ai/* และใช้ชื่อที่มีจริง
  - ส่ง loras แบบ JSON list สำหรับ Generate และข้อความ JSON list สำหรับ Edit
  - poll งานจาก /api/v1/jobs/<job_id> จน completed/failed
  - ใช้ result_url และ preview_url ตามที่ Backend คืน
  - ตั้ง reverse proxy/read timeout ให้รองรับงานที่ใช้เวลานานโดยตรวจ flow จริง

ลำดับ 4: ทำ acceptance flow ตาม BACKEND_PRE_DEMO_CHECKLIST.md
  - สมัคร/ล็อกอิน สร้างและแก้ไขภาพ ดาวน์โหลดผลลัพธ์
  - ตรวจสองบัญชีแยกสิทธิ์กัน
  - หยุด/เปิด AI และ restart Backend แล้วตรวจสถานะงาน
  - ทำ backup และทดลอง restore ฐานข้อมูลพร้อมภาพในสภาพแวดล้อมทดสอบ
  - บันทึกผู้ทดสอบ วันที่ job ID และผลจากเครื่องจริง

ลำดับ 5: รวมงานกับ main หลังตรวจระบบครบ
  - เปรียบเทียบ diff และแก้ conflict โดยรักษางานของผู้ร่วมทีม
  - รัน tests และตรวจ CI/Docker ตามที่ต้องใช้
  - การส่งเอกสารนี้ไม่ได้หมายความว่าได้ merge main หรือ deploy แล้ว


10. ข้อจำกัดทางเทคนิคที่ต้องรู้ก่อนต่อยอด
------------------------------------------------------------
  - Backend ใช้ ThreadPoolExecutor 2 worker ภายในโปรเซส ไม่มีคิวร่วมหลายโปรเซส
    ให้ใช้ 1 โปรเซสสำหรับเดโม; การขยายต้องออกแบบ Celery/RQ หรือคิวร่วมอื่น
  - ยังไม่มีระบบจำกัดขนาดคิว Backend แบบถาวรหรือ automatic retry ของงาน failed
  - db.create_all สร้างตารางใหม่ได้ แต่ไม่ใช่ migration ของ column เดิม
    หากเปลี่ยน schema ต่อ ต้องเพิ่มเครื่องมือ migration และสำรองก่อน
  - progress ของ AiEngine เป็นสถานะรวม GPU ไม่มี job ID ให้จับคู่กับเจ้าของงาน
    ยังไม่ได้เพิ่ม live percentage/ภาพระหว่างทางรายผู้ใช้ใน Backend
  - ยังไม่ได้เปิด API interrupt/skip ของ AI ผ่าน Backend เพราะกระทบงานรวม
    ต้องมีการจับคู่งานและตรวจสิทธิ์ก่อนพัฒนาการยกเลิกงานรายคน
  - job.ai_result มีเฉพาะ header ที่ระบบอ่านได้ ไม่ใช่พารามิเตอร์ Forge ครบทุกค่า
  - backup ฐานข้อมูลและคัดลอกภาพเป็นคนละขั้น ต้องควบคุมการส่งงานระหว่าง backup
  - PostgreSQL ตั้ง URL/ไดรเวอร์ได้ แต่ built-in backup รองรับเฉพาะ SQLite แบบไฟล์
  - ตัวอย่าง .env ไม่เปลี่ยนค่า .env จริงให้อัตโนมัติ
  - โค้ดอ่าน response ภาพก่อนตรวจขนาดพิกเซล ถ้าขยายใช้งานควรพิจารณาขีดจำกัด
    จำนวนไบต์และการอ่านแบบ stream ร่วมกับขีดจำกัดรูปภาพ
  - ยังต้องทดสอบการปิดโปรเซส/timeout ขณะ AI ทำงานจริงและการจัดการงานซ้ำ
    ผลทดสอบจำลองไม่ได้ยืนยันพฤติกรรม GPU หรือเครือข่ายจริง
